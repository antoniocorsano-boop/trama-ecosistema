# TRAMA — Roadmap documentale e operativa

**Data:** 23 settembre 2026  
**Stato:** GOVERNED ROADMAP / DOCUMENTATION-ONLY  
**Scopo:** evitare dispersione, duplicazioni e rilavorazioni collegando documentazione, asset, prodotto e gate reali.

## Principio

La roadmap non è una lista di funzionalità. È una sequenza di **riduzione dell’incertezza**: ogni fase deve lasciare una fonte più chiara, un confine più verificabile o un’esperienza più testabile.

## R0 — Baseline ecosistema

**Obiettivo:** disporre di una fonte unica per significato, authority, lessico, stato e asset.

Deliverable:
- dossier ufficiale;
- baseline repository;
- pagina di progetto;
- registro asset;
- regola di precedenza delle fonti.

Gate:
- nessuna contraddizione con ADR/contratti;
- distinzione reale / sviluppo / futuro;
- nessuna autorizzazione runtime implicita.

## R1 — Chiusura ECO-02/P1

**Obiettivo:** validare il percorso reale Arena → Docente OS su Tecnologia 2C.

Gate:
- prova umana end-to-end;
- nessun intervento tecnico correttivo durante il percorso;
- feedback percepibile;
- provenienza e decisione docente preservate.

## R2 — Atlas F3 Materiali + Risorse

**Obiettivo:** passare da file pubblici isolati a materiali contestualizzati per lezione.

Acceptance:
- journey classe → disciplina → lezione → materiali/attività;
- L1 e L2 distinguibili;
- provenance accessibile;
- risorse pubbliche reali;
- nessun account studente.

## R3 — Atlas F4 Mobile + LIM

**Obiettivo:** verificare due superfici native, non adattamenti tardivi.

Acceptance mobile:
- una decisione primaria per schermata;
- filtri e navigazione touch-first;
- reflow e accessibilità;
- offline/status quando applicabile.

Acceptance LIM:
- densità ridotta;
- leggibilità a distanza;
- attività di classe;
- step off-screen.

## R4 — Atlas F5 Exit

**Obiettivo:** certificare la coerenza curricolo → esperienza.

Gate:
- authority non confuse;
- mappa ed elenco equivalenti;
- L1–L4 coerenti;
- privacy-first;
- accessibilità;
- nessun segnale UI che suggerisca automazione non autorizzata.

## R5 — Consolidamento

**Obiettivo:** ridurre debito semantico e documentale prima di ampliare l’ecosistema.

Azioni:
- aggiornare STATUS;
- riallineare source registry;
- collegare specifiche e asset;
- eliminare duplicazioni;
- verificare nomenclatura;
- congelare una baseline release del dossier.

## R6 — Evoluzioni da valutare

Solo dopo R5:
- R3-P2 Curriculum pubblico;
- R3-P3 Student Learning Hub;
- R3-P5 Smart Navigation;
- R3-P6 Curriculum Health.

**R3-P4 Docente OS → Atlas** resta una decisione distinta e richiede un gate umano/runtime autonomo.

## Sistema degli asset

Ogni asset deve appartenere a una categoria:
1. istituzionale;
2. architetturale;
3. prodotto/journey;
4. roadmap/stato;
5. dimostrativo didattico.

Per ciascun asset registrare:
- versione;
- proprietario logico;
- fonte canonica;
- stato;
- uso consentito;
- eventuale superamento.

## Cadenza di manutenzione

Aggiornare la baseline quando:
- cambia una authority;
- viene autorizzato un runtime;
- cambia il modello dei contenuti;
- si chiude/apre una fase R3;
- cambia una regola privacy/accessibilità;
- un asset di baseline viene sostituito.

Le modifiche puramente visive che non cambiano significato non richiedono una nuova baseline concettuale.

## Definition of Done documentale

Una fase è documentata correttamente quando:
- esiste una fonte versionata;
- lo stato è verificabile;
- i gate sono espliciti;
- gli asset sono registrati;
- non esistono copie concorrenti autorevoli;
- un nuovo collaboratore può ricostruire il perché della decisione senza dipendere dalla chat originale.
